## 2026-10-11 — NICE와 Perfect 시각 구분 피드백

- 대상: 착지 연출 구현 `31d5e18`. 사용자가 직접 플레이한 피드백이며 브라우저·창 크기·도달 구간은 제공되지 않았다.
- 사용자 원문: “Nice 와 Perfect 의 효과음 차이는 있지만, 뭔가 이미지상으로는 같아보이는 느낌이 있네. 반동은 일단 그대로 놔둬도 될거 같음”.
- 평가: 현재 소리 차이가 느껴진다는 사용자 근거가 생겼다. 기존 시각적 차이가 충분하다는 가설은 이 피드백으로 지지되지 않았다. 반동은 유지하고 착지 입자의 형태·색·링 유무를 우선 조정한다.
- 조정: NICE를 짧고 작은 따뜻한 금색 원형 입자, Perfect를 큰 흰빛·금색 네 갈래 별과 두 겹 접점 링으로 구분한다. 반동·Perfect/X 팝·소리·판정·정착 시간은 유지한다. 현재 수치는 [연출 설계](design/feedback.md)를 따른다.
- AI 관측: Chromium PC·Pixel 7 터치 에뮬레이션에서 같은 90ms 시점의 NICE/Perfect를 캡처했다. NICE는 작은 금색 점, Perfect는 흰빛 별과 두 겹 링의 형태로 구분된다. 5·10·20개, 360×640의 Perfect, 동작 줄이기·정지·재개·재시작도 관측했다. 반동의 최대 눌림과 280ms 뒤 다음 동전은 이전 수치를 유지한다. 자동 회귀 스위트는 실행하지 않았다.
- 가설 상태: 조정된 형태가 화면에서 서로 다름은 관측으로 지지된다. 실제 플레이 중 더 쉽게 구분되는지는 사용자 재확인이 필요하다. 화면 형태의 확인과 사람의 구분 속도·쾌감을 구별한다. 산출물은 `test-results/feedback-differentiation/`의 PNG와 `observations.json`이다.

## 2026-10-11 — 착지 반동·Perfect 팝·소리 차이 관측

- 대상: 일반 성공 범위 변경 `f51fc69`와 연출 설계 이후의 작업본. 사용자의 구현 요청에 따라 [착지 연출](design/feedback.md)의 B 강도를 시작값으로 적용했다.
- 방법: Playwright로 Chromium PC·Pixel 7 터치 에뮬레이션·OS 동작 줄이기 환경을 열고 실제 Space·터치로 낙하했다. 개발 시간 제어로 착지 후 프레임을 고정해 Scene 크기·가시성과 HTML 숫자 transform을 읽었다. 점수·동전 좌표는 덮어쓰지 않았다. 자동 회귀 스위트나 사람의 손맛 검사는 아니다.
- 측정: 일반 착지 후 42ms의 새 동전 높이는 102→95.88, Perfect 후 54ms는 102→93.84 논리 px다. 180ms에는 원래 크기로 돌아오고 280ms에 다음 동전이 이동한다. Perfect 후 90ms의 문구는 320×160→345.6×172.8, 숫자는 1.08배이며 확대 기준점을 달리해 두 줄의 간격을 유지한다.
- 중단: Perfect 팝 중 정지하고 시간을 진행해도 잔여 610ms와 동전 크기가 그대로다. 성공 문구·입자는 숨는다. 3초 카운트다운 완료 후 같은 시점에서 다시 보이며 오디오 source 시작 횟수는 늘지 않는다. RESTART·HOME에서 효과와 콤보 표시가 초기화된다.
- 소리 관측: 기존 WAV 원본을 유지한 채 실제 Web Audio 재생 속도 약 0.88/1.24를 확인했다. 이는 청취 평가가 아니며 최종 금속성 질감이 좋다고 판단하지 않는다. 사용자 음소거에서는 master mute gain이 0이고 시각 구분은 유지된다. 착지 직후 Escape 정지로 재생 중 source가 한 번 종료되고 카운트다운·재개에서 다시 시작되지 않는 것도 별도로 관측했다.
- 접근성: 동작 줄이기 환경에서는 동전 표시 크기 166×102·숫자 scale 1을 유지하고 짧은 고정 접점 빛만 남는다.
- 화면: PC의 Perfect 최대 팝과 모바일 20개 밤 배경 캡처에서 금화·두 줄 피드백·다음 조작 영역이 구분된다. 초기 입자는 금화 색에 묻혀 보일 수 있어 크기·페이드 밝기를 소폭 높이고 시작 위치를 동전 윤곽 바깥으로 옮겼다. PC·모바일의 실제 입력으로 X10·X100 최대 팝을 관측했고 360×640의 X1도 직접 확인했다. 문구·숫자가 잘리거나 다음 동전 영역을 가리지 않는다. 오류 결과는 [검증 기록](VALIDATION.md)에 기록한다.
- 가설 상태: 짧은 반응과 기존 템포·중단 연동은 런타임 관측으로 지지된다. 더 쾌감 있고 소리가 기분 좋다는 가설은 판단 유보다. 실제 Android/iPhone과 포털 환경은 관측하지 않았다.
- 다음 플레이: PC에서 5·10·20개를 진행하며 일반/Perfect의 차이가 느껴지는지, 효과가 다음 낙하 타이밍을 방해하는지, 반복 소리가 거슬리는지 비교한다. 실기기 조정은 기존 요청대로 보류한다.

## 2026-10-11 — 일반 성공 범위 확대 후 브라우저 관측

- [결정] 사용자가 일반 성공 범위 확대를 요청했다. 현재 허용 범위는 [시작값](GAME_DESIGN.md#플레이-테스트용-시작값)을 따르며 Perfect·속도·첫 실패 종료 방식은 유지한다. 아래 2026-10-10의 미채택 제안은 당시 평가 기록이다.
- 방법: Chromium PC와 Pixel 7 터치 에뮬레이션에서 개발 시간 제어로 위치를 맞춘 뒤 실제 마우스·Space·터치로 낙하했다. 점수나 동전 좌표를 덮어쓰지 않았다. 사람의 성공률이나 실기기 입력 지연을 측정한 것은 아니다.
- 판정 관측: 양쪽으로 폭의 35%·45% 어긋난 착지는 NICE, 45.01%는 실패다. Perfect 경계 10%는 Perfect/X1, 10.01%는 NICE이며 첫 동전은 콤보에서 제외된다. 전체 검사 결과와 재실행 사유는 [검증 기록](VALIDATION.md)에 구분한다.
- 화면 관측: 이전 범위에서는 실패하던 35% 치우침과 새 성공 경계에서 동전이 실제 착지 위치에 쌓이고 NICE와 점수 2를 표시한다. 경계 밖 실패는 점수 1로 종료한다. 실패한 동전은 여전히 착지 높이에서 멈춘 모습이므로 새 경계에서도 시각적으로 지지돼 보일 수 있다. 이번에는 실패 연출을 바꾸지 않았다.
- 계산상 영향: 최대 속도에서 중앙을 지나는 일반 성공 시간 폭은 이전 약 153ms에서 약 230ms로 늘어난다. Perfect 시간 폭은 그대로다. 실제 성공률이 1.5배라는 뜻은 아니다.
- 가설 상태: 요청한 판정 확대와 Perfect 유지가 브라우저에서 재현된다. 실패가 덜 가혹하게 느껴지는지와 최종 난이도는 사용자 비교 플레이가 필요하다. 연출의 쾌감 개선은 후속 워크숍의 별도 주제이며 아직 합의한 연출 변경은 없다.

## 2026-10-10 — 많이 겹친 동전의 실패에 대한 사용자 피드백

- 방법: 사용자가 제공한 결과 화면 `SCR-20261010-ulmw.png`와 현재 판정·렌더 코드 검토. 이미지의 표시 기록은 이번 판 9개/개인 최고 53개, 이번 판·개인 최고 콤보 X4다. 정확한 실패 좌표·입력 시점·브라우저·빌드 식별자는 제공되지 않았다. 새로운 게임 실행·자동 검사·픽셀 계측은 하지 않았다.
- 사용자 관측: “동전이 이전 동전보다 절반도 안삐져나왔는데 게임오버인거는 너무 가혹한 느낌”. 실패의 시각적 납득 가능성에 대한 피드백이며 입력 누락 보고는 아니다.
- 코드 근거: 두 번째 동전부터 가로 중심 거리로 판정한다. 평가 당시 성공 경계는 0.30D로 D=166에서 좌우 49.8 논리 px였다. 현재 조정값은 [시작값](GAME_DESIGN.md#플레이-테스트용-시작값)을 따른다. 같은 폭의 동전을 가로 구간으로 보면 최소 약 70% 겹침을 요구한다. 실제 그림의 원근·투명 여백이 있어 화면의 정확한 겹침 비율과 동일한 계측값은 아니다.
- 평가: 절반 이상 겹쳤는데도 실패하는 상황은 현재 규칙으로 설명된다. 첨부 이미지의 정확한 위치를 복원한 결함 재현은 아니며, 이 자료에서 입력·착지 판정 버그를 확인한 것은 아니다. 사용자가 기대한 허용 범위보다 현재 성공 폭이 좁다는 조정 근거가 있다.
- 표시 근거: 낙하 동전은 착지 높이에서 멈춘 직후 실패 모드로 전환되고 결과 화면에도 남는다. 시각적으로 아래 동전 위에 얹힌 모습이므로 실패 이유를 더 읽기 어려울 수 있다.
- [제안] 비교할 다음 성공 경계는 중심 거리 ≤0.45D(좌우 74.7 논리 px)다. 가로 폭 약 55%가 겹치면 성공하며 현재보다 허용 구간이 1.5배 넓어진다. Perfect 경계·이동 속도·첫 동전·첫 실패 종료 방식은 이번 비교에서 유지한다. 이 수치는 미채택이며 코드에 적용하지 않았다.
- 계산상 영향: 최대 이동 속도 650 논리 px/s에서 한 번 중앙을 지나는 성공 시간 폭은 현재 약 153ms에서 제안값 약 230ms로 늘어난다. 실제 사용자 성공률이 1.5배가 된다는 뜻은 아니다.
- 가설 상태: 현재 판정의 실패가 시각적으로 납득된다는 가설에는 반대되는 사용자 사례가 생겼다. 전체 난이도·성공률은 판단 유보다. 제안 범위가 더 공정하게 느껴지고 Perfect 도전도 남는지는 변경 후 사용자 플레이로 확인해야 한다.
- 다음: 사용자가 제안값을 채택하면 성공 경계와 관련 회귀 검사를 변경하고, 양쪽 경계·이번 화면과 비슷한 치우침을 브라우저에서 확인한다. 이후 5·10·20개 구간에서 NICE 생존과 Perfect 도전의 체감을 비교한다.

초기 계측은 capture 리스너의 microtask에서 게임 핸들러보다 먼저 상태를 읽어 실패했다. 게임은 정상 낙하했고, 관측 시점을 bubble로 수정한 뒤 최종 2개 시나리오가 통과했다. 게임 동작은 변경하지 않았다. 연속 Perfect와 x4는 스크립트가 만든 결과이므로 자연 발생 빈도 근거가 아니다.

### 가설 상태와 다음 확인

| 가설                                            | 결과                                                            | 다음 확인                                                         |
| ----------------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------- |

밸런스와 피드백 시간을 유지했다. 다음은 PC·실제 휴대폰에서 짧게 반복 플레이하고, 기종/브라우저·판 수·도달 높이·속도 체감·Perfect 때문에 놓친 탭을 구분해 기록하는 것이다.

자동 측정만으로 재미·최종 난이도·터치 감각을 확정하지 않는다. 합의된 시작값은 변경하지 않았다. 다음 제안은 실제 Android/iPhone과 PC에서 짧게 반복 플레이하며 위 세 가설을 관찰하는 것이다.

화면 관측 중 일시정지 제목이 이동 동전을 일부 가리는 배치를 발견해 제목은 위로, 메뉴는 목표 아래로 옮겼다. 이후 검사에 제목·메뉴 경계와 하단 버튼 사이 간격을 추가했다. 이 배치 수정은 게임 수치나 판정 규칙을 바꾸지 않는다.

배포 화면에서 HUD 판 누락도 관측했다. CSS 배경 이미지 디코딩 검사로 실패를 재현하고 URL 기준을 수정했다. 배포 캡처도 다시 확인했다.
